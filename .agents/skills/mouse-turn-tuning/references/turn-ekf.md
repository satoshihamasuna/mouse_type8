# ターン時のEKFパラメータの同定

半径・Lstart/Lend・PID/FFの調整で取得した動画と走行ログを使い、ターン中の自己位置・滑り角を推定するEKFの係数候補も求める。
本手順の主対象はファームの固定6状態`[前方位置,左位置,姿勢,滑り角,ジャイロ零点,横加速度零点]`。
同定結果は候補として保存し、パラメータ反映・書込み・走行は依頼された範囲で行う。

## 実装と現在の適用範囲を確認する

- [Params/turn_pose_param.h](../../../../Params/turn_pose_param.h)：機体別・吸引別のK、観測雑音、初期零点の標準偏差、校正速度、適用制限。
- [Task/Inc/turn_pose_ekf.h](../../../../Task/Inc/turn_pose_ekf.h)：6状態モデル、Q/R・初期共分散、観測間隔、採否、静止零点校正、`eligible()`の対象条件。
- [Module/Src/interrupt.cpp](../../../../Module/Src/interrupt.cpp)：実測周期、単位・符号、吸引出力、適用箇所。ファームの`turn_x/y`は左/前のmm、解析の`x/y`は前/左のmを起点とするので対応を確認する。
- [解析README](../../../../tools/analysis/README.md)と[シェル仕様](../../../../tools/myshell_README.md#ターン自己位置ekf)：ツールの入力条件と`turn_ekf`の意味。壁側の`wall_ekf`・`wall_edge`とは別設定。

2026-11-18時点でファームが適用するのは、Aの非吸引500 mm/s・右90°と、吸引1600 mm/s・duty600～700の右90°/右180°。校正時の吸引はduty650。
非吸引右180°は比較で悪化したため対象外。左旋回・別速度・斜め進入/退出・探索・Bの採用をこの結果から決めない。
毎回実装と最新の検証記録を確認し、この日付の範囲を新たな校正結果より優先しない。

## 入力をそろえる

- 同一試行の`motion.csv`、`motion.settings.json`、動画、撮影・座標登録記録、全フレーム解析結果を対応付ける。機体、ファームの版、ターン、速度、吸引の明示的な真偽・実duty、電圧、PID/FF、壁モードを確認する。
- `turn_ekf show`のモードと実機係数の根拠も記録する。設定JSONに項目がなければ別の記録を添え、不明を推測で埋めない。起動時`control`でも全ターンへ適用されるとは限らない。`show`は最新状態であり、全走行中の採否履歴を復元するものではない。
- MCUの`time_ms`・`sequence`、`irq.period_us`、`ideal.velo`・`ideal.rad_velo`、`ego.velo`・`ego.accel`・`ego.rad_velo`・`ego.horizon_accel.get`を照合する。連続性・欠測と必要な静止点数は選ぶツールの実装で確認する。8状態版では車輪パルス等の追加列も必要。
- 同じ吸引状態・安定したdutyで走行前の静止区間を確保し、走行後も平均遅れを評価できる余裕を残す。吸引振動の大きい角速度サンプルを選択的に捨て、零点や雑音を小さく見せない。
- [撮影条件](capture-profiles.md)に従い、位置・向きを評価する各フレームのArUco登録と生の機体マーカー検出を確認する。動画の実PTS、MCUとの同期、マーカー高さ、カメラ高さ、前後マーカーと車軸/IMUの位置関係を保存する。中心IMU・マーカー中点を中心とする仮定が未実測なら、条件付きの結果と明記する。
- `ego.horizon_accel.get`がモデル値ではなく実測横加速度だったファームかを確認する。`ego.turn_slip_theta`やEKF適用後の位置を独立な真値にせず、動画の機首方向と移動方向から滑り角を観測する。
- 制御周期とCSV配信周期を区別する。20点平均と遅れは取得時実装に合わせ、行番号を1 msとして積分しない。`ego.velo-.010*ego.accel`による車輪平均速度の復元も、記録時の実装と単位が一致する場合だけ使う。

## 求める値と判断の根拠

| 項目 | 求め方・単位 | 反映先・注意 |
| --- | --- | --- |
| 滑り係数K | 静止零点を引いた横加速度と動画の滑り角から`ay=-K*beta`を当てはめる。betaはrad、Kはm/s² | 解析`k_m_s2`、ファーム`k_m_s2`。タイヤ単体の物性値ではなく条件付きの実効係数 |
| 横加速度観測標準偏差 | 同じ平均化を適用した動画betaに対する残差RMSE、試行間差、外れ値を評価。m/s² | 解析`ay_std_m_s2`、ファーム`acceleration_std_m_s2`。センサ雑音だけでなくモデル不一致・動画誤差を含む |
| ジャイロ入力標準偏差 | 吸引条件ごとの静止分散/MADと走行時の残差、量子化・間引きを確認。rad/s | `noise.gyro_std` → `gyro_std_rad_s`。静止で小さい値が出ても走行に必要な雑音下限を確認 |
| 初期零点の標準偏差 | 静止窓ごとのジャイロ/横加速度零点のばらつき。rad/s、m/s² | `initial_gyro_bias_std` / `initial_accel_bias_std` → 対応するファームの`initial_*_std_*`。各走行の零点平均と区別 |
| Qのモデル誤差・バイアス変動、初期姿勢/滑り分散 | 試行を分けた残差・共分散の整合と感度で候補を比較。状態とdtに応じた単位 | 6状態版の式を確認。8状態版の`wheel_slip_std`・`velocity_walk`を6状態版へ機械的に転記しない。識別不足なら既定/仮定と表示 |
| 観測間隔・NIS上限・共分散/差分上限 | 平均化による相関、棄却理由、誤適用を検証 | 同定係数と区別する。見かけの採用率を上げるために条件を緩めない |

解析の候補プロファイルは機体・速度・吸引ON/OFF・duty・左右/ターン形状の適用範囲を持たせる。
現行の選択キーは吸引真偽だけなので、別速度やdutyを追加する場合に既存条件を上書きしない。複数条件をまとめるなら、共通K・雑音で各条件を説明できるか検証して根拠を残す。
速度と吸引が同時に変わるデータだけでは吸引単独の効果を分離しない。励起不足、Kが探索境界に張り付く結果、同期・幾何誤差を係数で吸収する結果は採用候補にしない。

## 同定から比較まで

1. 幾何・PID/FFとEKFを同時に変更せず、取得時の推定方式を固定した基準試行を使う。既存の有効動画を再利用し、初めから全試行を取り直さない。
2. [turn_slip_conditions.py](../../../../tools/analysis/turn_slip_conditions.py)の`observe(raw, settings, pose, geometry, report)`で、登録済み動画とIMUの対応、滑り角・静止零点・同期・残差を求める。横加速度には同じ20点平均を施した動画betaを対応させる。
   `observation.frame`の`averaged_beta_rad`、`imu_left_m_s2`、`fit`を`force_fit()`へ渡してKを求め、条件別に集計する。このモジュールには同定用CLIはない。現在の関数はAと中心IMUを前提としており、Bは機体校正・幾何とツール対応を先に用意する。
3. 静止区間と力モデルの残差から雑音・初期零点分散の候補を作る。Q/R、初期共分散、ゲートのどれを変えたかを残す。旋回に合う自由な追加バイアスを与えない。光学姿勢とジャイロの尺度差は同期・撮影幾何も含む診断であり、機体のジャイロ尺度へ自動適用しない。
4. 同定に使わない試行で検証する。十分な独立試行があれば試行単位の除外検証を行い、Kと調整した雑音を評価対象試行から決めない。微分窓・平均遅れ・同期・高さの感度も比較する。検証試行不足や同定と評価の重複は明記する。
5. 同じ入口原点・入口方向・時間軸で従来積分、既存EKF、候補EKF、動画を比較する。推定方式ごとに回転/尺度/終点を合わせない。全区間/旋回中のRMSE、最大差、出口位置・方向、滑り角の残差、各試行の悪化、共分散・NIS・採用/棄却数を確認する。相対軌跡の改善を盤面固定の合格や絶対精度保証にしない。

現行の[turn_pose_profiles_A.json](../../../../tools/analysis/turn_pose_profiles_A.json)はA専用。
`turn_pose_ekf.py --slip-model`は保存済み係数を使う再生であり、この実行だけでは新しいKや雑音を同定しない。通常の8状態版と6状態滑り版を区別する。
6状態の事後再生にはNumPy・pandas・SciPyを使い、出力は新規ディレクトリへ保存する。
以下の`python`は必要パッケージを持つ環境に読み替える。このPCの既存例は`D:/venv/venv3-11/Scripts/python.exe`。`scipy.integrate.cumulative_trapezoid`も読み込めることを確認する。

```powershell
python tools/analysis/turn_pose_ekf.py --slip-model --log PATH_TO_MOTION_CSV --settings PATH_TO_SETTINGS_JSON --output PATH_TO_NEW_OUTPUT
```

現行CLIはAの既存プロファイルを読む。新しい候補は別ファイルへ保存し、読み込むプロファイルとハッシュを明示した再生用スクリプト等で比較する。候補を評価するだけのために既存プロファイルを上書きしない。
同定・比較の入力構造は[既存の条件別解析](../../../../tools/logs/turn_slip_conditions_A_20261118_v1/README.md)と同フォルダーの`analysis_source.py`・`evaluate.py`を参照できるが、これらは保存済み試行の固定パスと出力先を持つため、そのまま再実行して過去成果物を更新しない。

## ファームへつなぐ

- 事後再生は平均遅れを合わせる未来サンプルを使う。オンラインではその情報を使えないため、事後解析の改善だけでファーム採用を決めない。横加速度を予測と観測へ二重に使わず、旋回中の未校正IR距離を融合しない。
- ファーム反映も依頼されていれば、候補と現行値の差を確認し、機体別の`Params/turn_pose_param.h`と必要な実装へ反映する。解析JSONの更新はファームへ自動反映されない。`debug turn ... set`や`turn_ekf`にK・雑音の設定機能があると仮定しない。`turn_ekf`はモード選択・表示・リセット用。
- 実C++の因果的再生で、採用された周期の位置増分とフォールバックを動画基準に照合する。現行の軌跡比較/再生ツールはAの既存レポート形式を前提とし、再生はAでビルド、右90°/右180°の割当とPWM650/0を使用する。新しい機体・形状・dutyではその制約への対応を先に行う。5ms配信点の再生では欠けた1ms観測・MCUの処理負荷を復元できない。

```powershell
python tools/analysis/turn_trajectory_overlay.py --review PATH_TO_CONDITION_REVIEW --output PATH_TO_NEW_OVERLAY
python tools/analysis/turn_pose_firmware_replay.py --review PATH_TO_NEW_OVERLAY --output PATH_TO_NEW_REPLAY
```

上記`--review`は任意のCSV置場ではない。前者は条件別解析の`report.json`・試行別`observations.csv`等、後者は前者の`manifest.json`・`compare.html`を必要とする。実装で入力スキーマを照合する。
Python試作とC++ではゲート・観測間隔等も異なるため、同じ動作として扱わない。反映時は[mouse-build-check](../../mouse-build-check/SKILL.md)に従い、共有変更はA/Bビルドと該当する`test_turn_pose_ekf.py`・`test_turn_slip_conditions.py`・`test_turn_pose_firmware.py`等を確認する。
依頼された実機評価では停止中にモードを切り替え、まずShadowで推定・棄却・零点校正・IRQ処理時間を確認し、適用候補だけControlと従来方式を比較する。既存の対象外条件を係数が出たという理由だけで`eligible()`へ追加しない。
採用方式を決めた後、Lstart/Lend・出口方向・連続接続を再確認する。解析やビルドへ移る前の電源OFF案内はスキル本体の手順に従う。

## 保存・報告

入力パス・ハッシュ、機体/ファームの版、速度・吸引・左右/形状、座標基準と測定点、静止窓・同期・平均化・除外理由、実行コマンド/スクリプトを保存する。
候補JSONにはK・雑音・初期共分散と単位、既定/仮定の項目、校正域、試行数、同定/検証の分割、従来/既存/候補の比較、適用不可条件を残す。
「オフライン候補」「因果再生確認済み」「実機Shadow確認済み」「実機適用確認済み」を区別し、不足データと次に必要な条件を明記する。
