Python側は実装本体が出力したフレームを復号し、通知分割、CRC破損後の再同期、
CSV列・時刻・連番欠落を検証します。3 msフレームでもCRC再同期、CSVの実時刻・周期・欠落の保持を確認します。
既定周期は20 msのままです。要求許可範囲3～1000 msは実機での持続受信や走行中の安定性を保証しません。
上記の `test_mouse_ble_transport.py` には、
模擬BLE接続による自動開始・継続要求・逐次CSV保存・終了時の停止も含まれます。
実機での持続転送速度、制御周期への影響、電波条件は別途確認が必要です。

`test_mouse_ble_log.py` の `FirmwareTimingTests` は実際の送信・ログ実装と仮想時計を使います。
ADC周期1.018 ms・占有300 µs、1 ms SysTick、3 msログの位相を41通り変えて、
旧TX128 byte対照の待機キュー満杯を再現し、TX512 byteの順序・DMA領域保持と欠落なしを確認します。
占有550 µsの折り返し検証と、UART 230400 bpsでは新バッファでも帯域不足になる対照ケースを含みます。
CRC/HALの実CPU時間、DMAバス競合、BLEはモデル化しておらず、実機での3 ms受信を保証するテストではありません。
